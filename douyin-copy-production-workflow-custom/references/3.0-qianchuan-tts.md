# 3.0 千川热门原稿保留与直接 TTS 交付

## 使用场景

用户要求3.0、千川素材、保留热门原稿并植入固定CTA、全文1500字以内或直接交付TTS Word时，使用本流程。

正式提示词：

`/Users/kin/Documents/Codex/2026-07-02/gemini/work/25_feice_3_0_qianchuan_prompt.txt`

## 生成流程

1. 读取原稿全文，识别爆款开头、承诺数量、编号顺序、核心观点、原广告和原片尾。
2. 用正式3.0提示词替换原文占位符，以`--isolated`发送给Mac本地Gemini runner。
3. 自动选择CTA：聊天、方法、系统、多模块内容优先A；觉醒、逆袭、慕强、强者特质优先B。用户指定时服从指定。
4. 只压缩重复解释、过长案例和次要铺垫，不重新选题，不把原稿改成单一痛点。
5. 全文无最低字数，包含CTA绝对不超过1500个汉字，内部优先控制在1450以内。

## 长清单硬规则

- 原稿承诺的数量必须完整兑现，编号顺序不得变化。
- 三十六问等长清单也必须逐项出现，不得压成三个阶段或若干概述。
- 字数紧张时，先删实验故事、机制展开、案例拆解、操作演示和重复总结。
- 每项可压成一句最短口播，但核心问意或判断不得消失。
- 先为固定CTA预留完整字数，再给开头和全部清单项分配字数。

## 过桥硬规则

- CTA前最多一句过桥，也可以不加。
- 过桥必须收住本篇最后一个观点，并引出所选CTA的第一层含义。
- 禁止使用“这些问题需要一套系统理解”“你需要系统学习”等万能广告句。
- 禁止出现上一稿的数量、问题、类型或其他串稿词汇。
- 不重复课程名称、三大板块、260节或左下角入口，也不提前照抄CTA第一句。

## 验收

逐项检查：

- 原开头文字是否保留；只允许修复自然口播标点和确定无疑的错字。
- 原稿承诺数量、编号顺序和每项核心内容是否完整。
- 是否删除原作者、原账号、原CTA、进群引导和感谢观看。
- 是否只有CTA A或CTA B中的一条，且锁定CTA完整、只出现一次、位于全文末尾。
- 过桥是否贴合本篇且没有串稿。
- 汉字数是否小于等于1500，优先小于等于1450。
- 是否无拒绝语、提示词痕迹、标题、字数说明和`[[RISKNOTE]]`。

首次输出失败时，记录具体失败项并用同一完整提示词重跑；不要只发一句泛化重写命令。模型反复忽略长清单或字数预算时，可添加本篇硬约束，但不得改变3.0的母流程。

## 直接 TTS Word 交付

最终交付必须是纯净`.docx`，可直接导入TTS：

- 只含成稿正文，不含标题、作者、版本说明、字数、分隔线、CTA标签或后台备注。
- 使用正常中文段落和自然标点控制停顿。
- 不做字幕式短行，不限制每行17、20或22字，不逐句强制换行。
- Word自然自动换行是正常现象，不需要按页面宽度继续拆句。
- 不同类型、编号大项和CTA段落之间保留自然段落层次。
- 固定CTA保持原文字词、标点、顺序和段落结构。
- 默认字体Calibri 11磅，中文字体PingFang SC，1.25倍行距，段后6磅，Letter页面与1英寸页边距。
- 按抖音文案工作流进行DOCX包结构、正文一致性、CTA、字数、风险标记、文件大小和时间戳检查；不要调用LibreOffice或`render_docx.py`。
- 成稿同时保存到当前Codex输出目录和`/Users/kin/工作用（同步）/7.1后双端同步文件夹`，复制后用二进制比较确认一致。
