# 普通2.8验收：一次通读，按问题修，不重新设计

仅用于Gary普通2.8（包括承接新版huanxin短稿），不覆盖2.5、2.9、3.6、独立3.5、4.0、Ryan或千川。以下是普通2.8验收的统一入口；旧通用验收、返工和包装描述与本页冲突时以本页为准。完整2.8生成提示词不变，新增验收报告不送入扩写提示词。

## 1. 本地检查硬指标

以实际冻结标题、数量、主机制、强结果和短稿为合同，不重新抽机制或翻知识库。先保存原始扩写，不覆盖。默认正文最低3000中文字，不为凑6000—8000重跑；用户明确的新字数要求优先。运行scripts/check_28_draft.py，输出字数、片尾、后台词线索、哈希，不自动判语义通过。编号、案例和CTA由下一步核对，不能用关键词命中代替内容成立。

仅处理当前输出；换新历史已经复核的路线不再整库检查。新扩写若出现疑似旧案例、旧主题或明显新增重复内容，才按huanxin摘要优先去重补查相关记录。

## 2. 一次通读，合并核对

按顺序通读一遍，在同一份acceptance.json记录：

- 标题兑现：主机制与结果没有漂移，承诺的N点都有独立的动作及解释；不能只在案例里提到某点就算完成。
- 案例与转化：原合同要求的案例在中段CTA之前，问题、调整、可观察反馈和结果完整自然；必要的导读、豆包提示、中段/结尾CTA与固定片尾完整。用户明确要求扩写后的案例按真实案例原文保留，验收不改案例的人物、对话、过程、结果及措辞，不做去AI感替换；发现缺漏仅记录，不自行补写。用户说明不等于系统独立核实，报告不虚称已核实真实性。
- 稿件完整：没有明显截断、旧题残留或后台说明；术语及作用路径没有明显自相矛盾、张冠李戴。实际存在的确定问题才修，不每篇重新做全库来源验证。
- 口播：用户已授权验收时局部去AI感。仅在案例以外处理确定的错字、病句、读音歧义、僵硬身份标签、露出的字段名，以及明显重复的模板转折、机械排比、空泛抽象词堆叠、教案衔接和刻意拔高句。按humanize-copy的light模式，只改命中句及必要衔接；保持观点、机制、操作、力度及CTA，不整篇重写、不自动改温和，不为满足理想句式、段长、术语密度或六层模板返工。先标出完整案例范围并保存原文/hash，修改后核对案例逐字一致。

报告只保留合同/源稿hash、当前正文hash、每点的兑现位置、上述检查结论、确定的问题及修复记录。不写重复的长篇点评，不另算文风分数。无实质改动时复用这一次通读，不在匹配开头或导出时重复全篇验收。

## 问题怎样处理

| 情况 | 动作 |
|---|---|
| 完整且合同兑现 | 内容检查通过，进入正式开头及Word交付；状态仍为正文待确认 |
| 错字、病句、标签、后台词、片尾缺失或错字 | 有明确正确写法时局部修复，记录前后差异，不重跑扩写 |
| 少量漏点、CTA局部缺漏 | 先在本篇原路线内定向补齐；不改其他合格段落，保留原稿 |
| 案例缺项或出现疑点 | 记录待处理项并保留原文，不自行改写、补写或用新故事替换 |
| 无正文/拒绝/接口错误、全篇跑题或严重截断、整体明显不足 | 按普通2.8原会话规则重跑本篇，使用完整原提示与锁定源稿；不重跑整批 |
| 局部补齐一次仍不成立 | 记录具体未解决项；确须重跑再重跑本篇，不循环润色 |

每次修改后重查本地硬指标，并复核受影响的点、相邻衔接及其案例/CTA；观点数量、主链或全局结构被改变时才再通读。不同稿件hash不得复用旧验收结论。检查通过不等于用户认可、平台审核通过或已发布。

## 3. 正式开头与Word只核对交付

用户已锁定opening_lock时逐字装回，不重新匹配；没有正式开头才调用baokuan-kaitou-sheding。确认开头数量、机制和结果仍与正文一致，删除竞争开头，但保留既定导读/豆包/CTA桥段。上游已锁定标题和一个正式开头的当前流水线，不自动再做10个标题及三版开头；明确请求旧包装或多版对比时才做。

导出前保存完整交付文本及hash；Word导出后一次核对正文、开头和CTA与交付文本一致，检查DOCX包可读、实际路径、文件名和文件大小。发现导出错误修文件，不重新验收写作内容或重新扩写。不重复转PDF或渲染。默认放正文待确认，用户明确认可后才进入成品状态。

## 最小运行

```bash
python3 scripts/check_28_draft.py --draft expanded_raw.txt --output mechanical_check.json
```

check_28_draft只是机械事实检查；它不证明内容质量、案例、观点数量或平台安全。acceptance.json由执行者实际阅读后填写，包含source_sha256、draft_sha256、point_coverage、checks、issues、repairs、state。没问题时issues和repairs可为空；保留原文，不为了填写报告制造修改。
